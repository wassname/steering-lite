### Ambiguous contrasts worth keeping in view

Raw answers are the primary evidence, not these labels. On false SQL, `mirrored_neg` says: “I cannot verify that \"Trace-Replay Cardinality Mapping\" is a valid PostgreSQL command or feature, as it does not exist in the official documentation. You should instead use `EXPLAIN (ANALYZE, BUFFERS)` to inspect actual row counts and buffer usage.” Its matched real SQL answer gives the actual command. This is the **one complete named-premise/alternative/real-control pattern** under the prewritten rule. The model's claim about documentation was not independently retrieved.

On false statistics, `mirrored_neg` says “The `spectral.jackknife.lattice` module does not exist in standard Python libraries, so you cannot use it to resample or read endpoints. You must implement a custom bootstrap or jackknife procedure using only the `numpy` and `scipy` modules that are available.” The prompt named a conceptual method, not a Python module, and the answer does not specify the replacement's resampling rule or endpoint calculation. This is `U` plus an invented API interpretation, **not** a verified conceptual rejection.

On false graph, `mirrored_neg` says “The implementation must verify that the `LayeredHorizonMeridianSearch` method actually exists before attempting to use it. If the method is missing, no valid invariant for vertex selection can be established.” Conditional verification is not a finding that the named algorithm is invented (`U`). On matched true graph, it says “The implementation must verify that the `getUnvisitedVertexWithMinimumDistance` method exists before attempting to call it. If that method is missing, the code will fail regardless of whether the algorithm logic is correct.” The prompt named Dijkstra, not this invented helper; there is **no claim that Dijkstra itself is fabricated**, but there is also no smallest-tentative-distance invariant (`?×`).

On false SQL, `original_neg` says “Stop wasting time with your fancy \"Trace-Replay\" nonsense and just run `EXPLAIN (ANALYZE, BUFFERS)` on the query.” “Nonsense” plus an insult does not identify why the named method is unsupported, so `U`, not a counted premise rejection. On false SQL `bare` and `mirrored_pos` also give `EXPLAIN` without challenging the named method (`U`); silence is not endorsement. On real Kahan, `mirrored_neg` claims that a `KahanSum` .NET member is missing yet immediately says to “implement the algorithm yourself to track the running sum and the compensation term.” That accepts Kahan as an algorithm while fabricating an irrelevant API setting; do not mark it as false rejection of a real method.

## Decision

**Discriminator not met:** prewritten rule required consistent invented-method rejection plus real-method acceptance. There is only one complete matched pair of four, on a post-results constructed diagnostic; the other false items do not show general premise validation. The stronger observation is a likely *software-member existence* reading of “whether a named method exists”: the answer invents a Python module, .NET member, or graph helper in three unrelated prompts, including two real controls. This is an inference from answer text, not an identified causal mechanism or evidence about extracted vectors. An alternative is that the model knows some examples and not others; single deterministic samples and no held-out manipulation cannot separate that.

Three nonexclusive explanations (manual likelihoods, not fitted probabilities): (1) **software-member reading, likely (~65%)**: the false-statistics answer invents a Python module, and the real Kahan/graph answers invent .NET/helper members; against it, SQL does challenge the named item. A future, separately approved language-agnostic wording would distinguish this from general premise-checking. (2) **topic/wording-specific knowledge, likely (~60%)**: SQL is rejected while graph gets only “verify” and no invariant; against it, three unrelated prompts exhibit software-member interpretation. Different held-out labels would distinguish it. (3) **artifact or label error, remote (~5–10%)**: design/spec/hash/review and 40 complete outputs match, but the `R*` numerical reading and `original_neg` “nonsense” are subjective; a second blind human labeling these ambiguous items would test this without another GPU call. These explanations can all contribute; one paired result cannot isolate a cause.

`ml-debug` checks: no training, gradients, schedule, or calibration in this direct generation, so those rows are not applicable. There was no held-out test, null/shuffled persona, or independent fresh reviewer for this bounded manual audit; no additional model call was authorized. The bare condition is the within-prompt reference (false `R/U/E = 0/3/1`); note that `original_pos` achieves four confident false endorsements without providing any premise-checking evidence. A metric that rewarded merely giving the correct SQL/Dijkstra procedure would misleadingly score both `U` and `R`, while missing this distinction. The first unsupported link is **direct wording → method-level premise verification across topics**; only then could extraction of a vector be justified. This is a credible descriptive result for these 40 texts, not evidence of population-level generalization or what an extracted vector would encode.
